Motivation

PatchBench (Shen et al., 2026) evaluates 11 patching agents on 213 C/C++ tasks and finds that checking only the original PoC inflates the solve rate 1.83x on average: 83.1% of agent patches eliminate the original PoC crash, but only 45.3% of tasks pass both security and semantic validation (Section 5.2, Finding 1).

The same gap applies to the reference patches that agent patches are graded against. A developer patch that only masks the symptom passes the same PoC check. PatchBench discards tasks whose reference patch is orthogonal to the root cause (Section 4.2) but does not report how many.

Example: mruby.cve-2022-1276 (below). PatchBench cites its developer patch as one that "eliminates the root cause" (Section 2.2), yet after that patch 66 of 103 index assignments still get a wrong argument, with no crash and an unchanged test suite. 3 of the 6 instances recorded so far have such a developer patch (dev_patch_fixes_root_cause in results.jsonl), so each instance needs a reference patch checked against the root cause, not only the PoC.

The 103 cases

  • Synthetic cases that target the root error, not the PoC; written after the root cause was found, not from the dataset or test suite.
  • Root bug: off-by-one in the register stack after the keyword hash, for every positional count 0-13. At 13 the VM reads an Integer as the argv array (OOB read, the PoC); at 0-12 no crash, but the callee silently gets a wrong last argument.
  • Developer fix special-cases count 13 (the one the report hit); root-cause fix removes the off-by-one and covers all 14 counts.

Checks added

  • Predictions before the run - predict each case's result (OK / wrong / ASan) on every build before running; scripts/check_predictions.py fails on any mismatch, so the root cause is a checked prediction set, not a story.
  • Developer-model column - the same predictions from the developer's own explanation; whatever it fails to predict becomes a logged count.
  • Assertion variant - a temporary check at the exact point where the invariant must hold stops the program with a fixed message (STACK-INVARIANT) the moment it breaks, instead of crashing later or silently giving a wrong value; it must fire on exactly the predicted bad cases without the fix, on none with the root-cause patch, and never on the project's own code (here every Ruby file in the source tree).
  • Blind second reading - a sealed-off reader gets only the report, PoC and base source and states the invariant and failing inputs; the patch is revealed in later phases, and agreement is scored per dimension before and after adjudication.
  • Separability rule - a second defect counts as independent only if its fix and the root fix repair disjoint case sets; "independent" becomes a test result, not a judgment.
  • Oracle pin - the program and version that gives the expected output (here CRuby 2.7.0 in the image).
  • Falsification and confidence - each record names the observation that would refute it and a high/medium/low rating with a reason.
  • Patch inventory - results.jsonl lists every patch: role, hash, source (upstream/backport/secbench/synthetic), what it fixes, status.
  • Tables from logs - case tables are rendered by scripts/render_cases_table.py, never typed from memory.

Questions

  • Is this rigorous enough for an ACL resource paper (decision rules, agreement between readers, provenance, limitations), and if not, what is missing?
  • When the developer patch does not fix the root cause and no developer commit anywhere (branches, tags, pull request heads, issues) fixes it, what goes in the dataset: the developer patch alone with a "does not fix the root cause" label, a synthetic root-cause patch marked as such, or neither?
  • Do we stay with the bug as outlined by the report and the developer (here a crash at 13 arguments), or do we infer the root cause (here an off-by-one for 0 to 13 arguments with 66 silent wrong values)? If we infer, what is the acceptance bar: predictions, assertion, second reading, or all three?
  • How do we define the scope of our own synthetic patch: only the faulty state the PoC reaches, every input that violates the same invariant, or every defect the cases find in the same code? (Here a second defect in gen_hash() is separable by the rule above but sits in the same branch.)
